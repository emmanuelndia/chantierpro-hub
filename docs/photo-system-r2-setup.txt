ChantierPro - Memo systeme photo + configuration Cloudflare R2

1. Ce que fait le systeme photo

Le module photo backend ajoute :
- POST /api/photos
- GET /api/photos/:id
- GET /api/photos/:id/content
- GET /api/sites/:id/photos
- DELETE /api/photos/:id
- GET /api/photos/logs
- DELETE /api/photos/logs/:id

Fonctionnement :
- upload en multipart/form-data
- stockage prive dans Cloudflare R2
- aucune URL publique permanente
- lecture via /api/photos/:id/content ou URL R2 presignee interne valable 15 minutes
- suppression logique uniquement
- creation automatique d'un PhotoDeletionLog immuable


2. Regles metier importantes

Roles autorises a prendre des photos :
- SUPERVISOR
- COORDINATOR
- GENERAL_SUPERVISOR
- PROJECT_MANAGER
- DIRECTION
- ADMIN

Roles autorises a supprimer une photo :
- PROJECT_MANAGER
- DIRECTION
- ADMIN

Visibilite :
- SUPERVISOR voit uniquement ses propres photos
- COORDINATOR, GENERAL_SUPERVISOR, PROJECT_MANAGER, DIRECTION voient toutes les photos du site selon leur perimetre
- ADMIN est autorise

Suppression :
- soft delete seulement
- isDeleted = true
- deletedAt renseigne
- deletedById renseigne
- creation d'un PhotoDeletionLog

Logs de suppression :
- consultables uniquement par DIRECTION et ADMIN
- immuables
- DELETE /api/photos/logs/:id renvoie toujours 403


3. Champs attendus a l'upload

Route :
POST http://localhost:3000/api/photos

Body :
multipart/form-data

Champs obligatoires :
- file
- siteId
- category
- timestampLocal

Champs optionnels :
- description
- lat
- lng
- planningAssignmentId

Exemple :
- file = <IMAGE_FILE>
- siteId = <SITE_ID>
- category = PROGRESS
- description = Photo de suivi chantier
- lat = 5.361349
- lng = -4.0083
- timestampLocal = 2026-04-26T08:00:00.000Z


4. Contraintes techniques

- taille max photo : 10 Mo
- si > 10 Mo : reponse 413
- si > 5 Mo : compression automatique serveur qualite 80%
- capture mobile deja encodee en JPEG
- storageKey jamais expose au client
- URL R2 presignee expire apres 15 minutes
- affichage canonique via /api/photos/:id/content

6. Configuration Cloudflare R2 a faire

Tu dois creer :
- un bucket prive Cloudflare R2
- une cle API R2 avec droits Object Read/Write sur ce bucket

Variables d'environnement a ajouter dans .env.local et Vercel :

STORAGE_URL=https://storage.example.com/chantierpro
R2_ACCOUNT_ID=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
R2_ACCESS_KEY_ID=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
R2_SECRET_ACCESS_KEY=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
R2_BUCKET=chantierpro-photos

Variable optionnelle :

R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com

Description :
- STORAGE_URL : valeur de secours pour le mode mock local
- R2_ACCOUNT_ID : Account ID Cloudflare
- R2_ACCESS_KEY_ID : Access Key ID R2
- R2_SECRET_ACCESS_KEY : Secret Access Key R2
- R2_BUCKET : nom exact du bucket prive
- R2_ENDPOINT : endpoint S3 R2; si absent, l'application le derive depuis R2_ACCOUNT_ID

Important :
- le bucket doit rester prive
- ne jamais servir d'URL publique permanente
- toute lecture applicative doit passer par /api/photos/:id/content


7. Etapes de configuration Cloudflare R2

1. Ouvrir le dashboard Cloudflare
2. Aller dans R2 Object Storage
3. Creer un bucket prive, par exemple :
   chantierpro-photos
4. Aller dans Manage R2 API Tokens
5. Creer une cle avec acces au bucket :
   - Object Read
   - Object Write
6. Copier :
   - Account ID
   - Access Key ID
   - Secret Access Key
   - Bucket name
7. Ajouter ces valeurs dans .env.local et dans Vercel
8. Redemarrer l'application


8. Migration depuis Supabase Storage

Le code priorise R2 si les variables R2 sont configurees.
Si R2 n'est pas configure, le fallback Supabase reste disponible temporairement.

Les nouvelles photos seront stockees dans R2.
Les anciennes photos stockees dans Supabase peuvent rester lisibles tant que les variables Supabase restent presentes.

Pour une migration complete des anciens objets :
1. Exporter les objets Supabase Storage.
2. Les uploader dans R2 en conservant exactement le meme storageKey.
3. Conserver les lignes Photo en base.
4. Verifier que /api/photos/:id/content retourne 200.
5. Retirer les variables Supabase uniquement quand toutes les anciennes photos sont migrees.

10. Checklist Postman

Login :
- POST /api/auth/login
- recuperer accessToken

Upload photo :
- POST /api/photos
- Body = form-data
- Authorization: Bearer <ACCESS_TOKEN>

Lire une photo :
- GET /api/photos/<PHOTO_ID>/content

Lister les photos d'un site :
- GET /api/sites/<SITE_ID>/photos?page=1

Supprimer une photo :
- DELETE /api/photos/<PHOTO_ID>
- body JSON :
  {
    "reason": "Photo floue ou non conforme"
  }

Lire les logs :
- GET /api/photos/logs?page=1

Tester l'immuabilite :
- DELETE /api/photos/logs/<PHOTO_LOG_ID>
- attendu : 403


11. Cas de validation a tester

- SUPERVISOR upload une photo valide -> 201
- PROJECT_MANAGER upload une photo -> 201
- fichier > 10 Mo -> 413
- fichier entre 5 Mo et 10 Mo -> compression automatique
- GET /api/photos/:id/content -> 200
- SUPERVISOR ne voit que ses propres photos
- SUPERVISOR tente DELETE /api/photos/:id -> 403
- PROJECT_MANAGER supprime une photo avec raison -> PhotoDeletionLog cree
- DELETE /api/photos/logs/:id -> 403 pour tous
- Sans variables R2, fallback Supabase/mock fonctionne encore en local
